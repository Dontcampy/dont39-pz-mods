# Design: processor refactor

## Target layout

`zabric-processor/src/main/java/com/pzlauncher/zabric/processor/`
- `ZabricProcessor` — rounds, `@Patch` / stray-annotation policing, file generation (~200 lines).
- `JavacHookReader` (new) — javac elements → `HookDecls` (read, gate, handler, checkMixin, target + bridges,
  supertypes, byBinaryName, annotation-mirror helpers).
- `glue/HookAnalyzer` — entry point and shared `failed` state; delegates to:
  - `glue/HandlerBinder` (new) — shape, member/overload resolution, `bindInject`, `bindModify`, modifiedArg.
  - `glue/PatchBuilder` (new) — patch assembly, share/always consistency, access checks, matcher simulation, naming.
- `glue/Messages` — gains the shared texts.

`zb-kt-utils-processor/src/main/kotlin/com/dont39/pz/zbktutils/processor/`
- `GlueProcessor.kt` — hooks only.
- `LuaBridge.kt` (new) — `@LuaGlobal` collection, rendering, `kotlinString`.

Shared failure state: `HandlerBinder` and `PatchBuilder` receive the analyzer's reporter/context object rather than
duplicating `failed`; order of reported errors must not change (HookRulesTest asserts messages).

## KSP tests

- Preferred harness: kotlin-compile-testing fork (`dev.zacsweers.kctfork`) with KSP2, if a release supports Kotlin
  2.4.21 / KSP 2.3.12. Otherwise run KSP2 programmatically (`symbol-processing-aa-embeddable`,
  `KotlinSymbolProcessing`) over temp source dirs. Decide at step 1 by a spike; record which in the task report.
- Test classpath: zabric API jar (project dependency) and stubs for game types the fixtures reference; no game jar.
- Golden files live under `src/test/resources/golden/`, like the javac side.

## Compatibility

Processor jars are published (`zabric-processor` on Maven Central). Only internal classes change; the processor's
options, generated output and messages stay the same. Version bump is the release step, not this task.

## Rollback

Each requirement is its own commit; the golden diff (AC3) is the gate for every commit.

## Implementation notes

- KSP test harness (spike): kctfork `dev.zacsweers.kctfork:ksp` 0.14.0, built on KSP 2.3.12 and Kotlin 2.4.20, runs
  `GlueProcessor` through KSP2 (`configureKsp`). On success it also compiles the fixtures and the generated glue, so
  the tests check that the glue compiles. Test classpath (`inheritClassPath`): `:zabric`, `:zb-kt-utils` (the real
  `Feature` and `@LuaGlobal`) and `ZombieBuddy.jar` from `pzDir`. The only stub is the game's `LuaMethod`. The harness
  is `zb-kt-utils-processor/src/test/.../Ksp.kt`; golden sources and expected output are under
  `src/test/resources/golden/`. The expected output was generated by the code before the refactor.
- R5 deviation: one `HandlerBinder` was 492 lines, so the parameter binding for one target (`bindInject`,
  `bindModify` and their steps) is its own class, `HandlerBinding.java`. `HandlerBinder` keeps shape, member
  resolution and the `bind` entry. Their shared state (types, reporter, `failed`, `descriptor`, `isVoid`) is
  `Analysis.java`. `Site` is in `PatchBuilder`; `Resolved` and `Shape` are in `HandlerBinder`.
- R3: `render` and `isType` moved to `KspTypes.kt`, because `HookReader` uses them too. `label` is a top-level
  function in `GlueProcessor.kt`. Writing the bridge files stays in `GlueProcessor`, which owns the `CodeGenerator`.
- R4: besides the three listed messages, `Messages.handlerTypeParameters` was also shared (word for word on both
  sides).
- R6: `Reporter` has one method now, so both front ends pass a lambda.
- Not moved: `ZabricProcessor.defaultClassName` (research P4, optional). The javac `HookRulesTest` calls it, and
  AC2 does not allow editing those tests.
- AC1 mutation check: each break below made at least one test fail. Broken rules: `@Thrown` nullability,
  target-value nullability, facade count, facade top-level only, top-level object, hook object visibility, handler
  extension, Lua bridge output, Lua prefix, Lua nested owner, Lua visibility, descriptor array parsing, glue callee
  (golden). One mutation, dropping the companion check of `@LuaGlobal`, was not caught because it changes nothing: a
  companion's parent is never top-level, so the next condition rejects it.
