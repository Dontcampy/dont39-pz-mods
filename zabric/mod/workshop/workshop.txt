title=Zabric
description=[h1]Zabric[/h1]
description=A small loader layer for ZombieBuddy Java mods, made by Dont39. It is not made by ZombieBuddy's author.
description=It does nothing on its own. Mods that need it require it; subscribe to it along with them and enable it.
description=
description=[h2]What it does[/h2]
description=[list]
description=[*]Opens up game and mod internals that installed mods list, so that they can use them directly. This has to happen when the game starts, before the game loads them, so Zabric runs at game start for every installed mod's list, whether that mod is enabled or not.
description=[*]Runs the code that mods built on it declare, in two phases: once when the game starts, and once when the mod list loads. Their order in the mod list does not matter. A mod with code for game start is kept running at game start: on its first launch Zabric registers it with ZombieBuddy, and from then on ZombieBuddy runs it at game start.
description=[*]Runs the hooks that mods built on it put into game and mod code, only while that mod is in the mod list. When a hook fails, that mod's hooks (or the part of the mod it belongs to) are switched off instead of breaking the game, and console.txt says which hook failed.
description=[*]When a mod takes effect only after a restart (it was just registered, or it was installed or updated while the game ran), a message on the main menu lists it. On a dedicated server the list is a line in the log.
description=[*]Changes no game files and nothing in your saves.
description=[/list]
description=
description=[h2]Requirements[/h2]
description=[list]
description=[*][url=https://steamcommunity.com/sharedfiles/filedetails/?id=3619862853]ZombieBuddy[/url] 2.3.4 or newer with its Java loader installed (it asks you once to approve this mod's Java code).
description=[*]Project Zomboid 42.21
description=[/list]
description=Load order: after ZombieBuddy. The code Zabric runs for the mods built on it does not depend on their order; a mod that must load after another declares it. On the first launch Zabric registers itself and those mods with ZombieBuddy and asks you to restart the game once.
description=
description=[h2]Note on approval[/h2]
description=ZombieBuddy asks you to approve a mod's Java code when it loads with the mod list. Code that runs at game start comes before that question: after an update of Zabric, or of a mod registered through it, the new version runs at the next game start before ZombieBuddy asks about it. Zabric registers only mods whose Java code ZombieBuddy approved and loaded.
description=
description=[h2]For mod authors[/h2]
description=[list]
description=[*]Opening up members: put a list at META-INF/zabric/<your mod id>.classtweaker in your jar. The first line is "zabric-classtweaker v1", then one directive per line, Fabric access widener style with internal names and JVM descriptors: "accessible class", "accessible field", "mutable field", and "accessible method" for constructors (<init>) only. Call com.pzlauncher.zabric.widener.AccessWidener.problem(modId, aClassInYourJar): null when your list is in effect, otherwise the reason.
description=[*]Entrypoints: name your classes in your jar's manifest; your mod needs no ZombieBuddy Main or PreMain for them. "Zabric-Main: <class>" (implements com.pzlauncher.zabric.entrypoint.MainEntrypoint) is called once per session, after ZombieBuddy has loaded the mod list, if it approved and loaded your mod. "Zabric-PreLaunch: <class>" (implements PreLaunchEntrypoint) is called once per launch, after ZombieBuddy has preloaded every jar and before the game starts: plain Java, no Kotlin, no game classes and no game log; keep what to report and report it from your main entrypoint. The class is a Kotlin object or has a public no-arg constructor. The order within a phase is undefined; an entrypoint that fails is logged with your mod id and the others still run. Mods that use only ZombieBuddy run their Main before any main entrypoint, so do not publish anything they need before then.
description=[*]Running at game start: a preLaunch entrypoint also needs javaPreload=true in mod.info and "ZB-Preload: true" in your manifest. Zabric then keeps your mod preloaded, using the mod id ZombieBuddy recorded for your jar; you ask for nothing. Require Zabric in mod.info; your entrypoints need no load order relative to it or to other mods. Classes are another matter: ZombieBuddy loads every class of your javaPkgName and applies your hooks when it reaches your jar, one jar after another, so if your code there uses another mod's classes, load after that mod (loadModAfter). Zabric's own classes are always there on a launch that runs entrypoints.
description=[*]Java mods and mod folders (package com.pzlauncher.zabric.mods): call from your main entrypoint or later, on the main thread; the calls throw when Zabric did not run at game start or its entrypoints stopped.
description=[*]JavaMods: loaded() lists every jar ZombieBuddy loaded in this game session (mod id, path, SHA-256, and LoadPhase PRELOAD at game start, STARTUP in the first mod list, LATER when joining or leaving a server); lastPass() the jars of the latest mod list; servingJar(package) the loaded jar the game runs that package's classes from. A jar stays loaded until the game exits.
description=[*]LaunchOverride: request(Workshop item id -> absolute path of a folder of mod folders) makes the next launch of the same side (client or dedicated server) use that folder in place of the item's mods folder, in every mod list of that launch, Lua and Java alike. The next game start reads and deletes the request; an invalid one is discarded whole, with an error in console.txt, which also names each item it uses. Items that hold ZombieBuddy, Zabric or ZabricKotlin are refused. pending() is what the next launch reads, current() what this launch uses.
description=[*]WidenRoots: add(folder of mod folders) makes Zabric read the widening lists of the mods in it from the next game start on, while the folder exists; scanned(folder) tells whether this launch read them. A LaunchOverride's folders are read without it.
description=[*]Relaunch (package com.pzlauncher.zabric.relaunch, same calling rules): restart(argument indices to leave out) quits the game and starts it again with the same program, command line, working folder and environment, minus those arguments, through a small helper process; it throws and leaves the game running when that cannot be set up. unavailable() is null when a restart is possible, otherwise the reason (Windows clients only). arguments() is this launch's argument list. When the game cannot start again after it quit, the player gets a message box, Zabric/relaunch.log in the game's cache folder, and a notice on the next main menu.
description=[*]Hooks, setup: compileOnly "com.pzlauncher:zabric:<version>" and annotationProcessor "com.pzlauncher:zabric-processor:<same version>" (Maven Central), plus the game jar and ZombieBuddy.jar from your install (compileOnly). Processor options: zabric.modId (your mod id) and zabric.javaPkgName (the generated glue goes there), plus zabric.glueClass when one mod is built from several compilations. The processor checks each hook at compile time and writes the loader glue into your jar.
description=[*]Hooks, API (package com.pzlauncher.zabric.hook; Mixin and MixinExtras names): @Hooks(Target.class) marks a final class of static handlers (targets = "a.b.C" for classes you cannot name; in Kotlin a top-level object). @Inject(method = "name", at = @At("HEAD" or "RETURN")) runs a handler there, with a CallbackInfo; cancellable lets it skip the target at HEAD or set the return value. @ModifyReturnValue returns a new return value. @ModifyVariable(at = @At("HEAD"), argsOnly = true) returns a new argument. @Share("key") LocalRef passes a value between the handlers of one call. Zabric only: @Self is the target's this; @At("FINALLY") runs after the target returns, throws or was cancelled (@Thrown Throwable), to undo what HEAD changed; always = true runs a handler while its gate is inactive too. Overloads need "name(descriptor)". Anything else (other @At values, @Redirect, ...) is a compile error.
description=[*]Hooks, gates: a hook class without a gate uses your mod's default gate: the first exception from a handler, or a hook ZombieBuddy did not weave, stops all your mod's hooks for the session, logged as "[Zabric] <mod id>: hooks stopped ...". For a smaller scope, name a gate in @Hooks(gate = ...): a HookGate with a public static final INSTANCE, or a Kotlin object. Its active() is checked on every call; its failed() gets what handlers throw and hooks that were not woven. A thrown exception never reaches the hooked method, which goes on as without the handler. Zabric checks the targets of default-gate hooks itself; a gate of your own calls ZabricHooks.gateProblem(gate) before it turns active.
description=[*]Hooks, timing and order: hooks run from the first mod list Zabric processes (when main entrypoints run) and only while your mod is in the mod list. They add no restart of their own. Across mods, the load order decides which hook wraps which; there is no priority. Within your mod, hook classes run by name and their handlers in declaration order.
description=[*]Hand-written ZombieBuddy @Patch classes: the processor rejects them. @UnsafeLoaderPatch on the class lets it compile, with a warning. Not recommended: such a patch has no Zabric gate, error catching or target check, and Zabric takes no responsibility when it breaks, e.g. when Zabric moves to another loader.
description=[/list]
