# Zabric for mod authors

Zabric is the loader layer for ZombieBuddy Java mods (Workshop item 3820726385). This is its author contract; the
Workshop page links here. A complete author build is in [`samples/zabric-java-hooks`](../samples/zabric-java-hooks).

What it does for players: opens up the game and mod internals that installed mods list (at game start, for every
installed mod's list), runs the entrypoints and hooks of the mods built on it (hooks also from game start for a mod kept
running then; a failing hook stops that mod's hooks, not the game), and lists on the main menu the mods that take effect
only after a restart. It also gives Java mods that load only when you join a server (or reload mods in the main menu)
the global Lua functions ZombieBuddy leaves out then. It changes no game files and nothing in saves.

Approval: ZombieBuddy asks to approve a mod's Java code when it loads with the mod list. Code that runs at game start
comes before that question: after an update of Zabric, or of a mod registered through it, the new version runs at the
next game start before ZombieBuddy asks about it. Zabric registers only mods whose Java code ZombieBuddy approved and
loaded.

- Opening up members: put a list at META-INF/zabric/&lt;your mod id&gt;.classtweaker in your jar. The first line is "zabric-classtweaker v1", then one directive per line, Fabric access widener style with internal names and JVM descriptors: "accessible class", "accessible field", "mutable field", and "accessible method" for constructors (&lt;init&gt;) only. Call com.pzlauncher.zabric.widener.AccessWidener.problem(modId, aClassInYourJar): null when your list is in effect, otherwise the reason. A class that first loads while ZombieBuddy weaves patches into an already-loaded class is not widened, so before ZombieBuddy applies a jar's patches Zabric loads the member types and nest members of the classes they name by exact name (for a class not loaded yet, those its class file names, leaving the class itself unloaded); with a name pattern, or a ZombieBuddy Main that loads its targets, such a class can still miss your list, which problem() then reports.
- Entrypoints: name your classes in your jar's manifest; your mod needs no ZombieBuddy Main or PreMain for them. "Zabric-Main: &lt;class&gt;" (implements com.pzlauncher.zabric.entrypoint.MainEntrypoint) is called once per session, after ZombieBuddy has loaded the mod list, if it approved and loaded your mod. "Zabric-PreLaunch: &lt;class&gt;" (implements PreLaunchEntrypoint) is called once per launch, after ZombieBuddy has preloaded every jar and before the game starts: no game classes and no game log, and Kotlin only as ZabricKotlin's README allows; keep what to report and report it from your main entrypoint. The class is a Kotlin object or has a public no-arg constructor. The order within a phase is undefined; an entrypoint that fails is logged with your mod id and the others still run. Mods that use only ZombieBuddy run their Main before any main entrypoint, so do not publish anything they need before then.
- Running at game start: a preLaunch entrypoint also needs javaPreload=true in mod.info and "ZB-Preload: true" in your manifest. Zabric then keeps your mod preloaded, using the mod id ZombieBuddy recorded for your jar; you ask for nothing. Require Zabric in mod.info; your entrypoints need no load order relative to it or to other mods. ZombieBuddy preloads in the order Zabric keeps: Zabric first, then each preloaded mod after the preloaded mods it requires in mod.info (require), the rest in the order they were registered; mods that require each other keep that order, with an error in console.txt. Classes are another matter: ZombieBuddy loads every class of your javaPkgName and applies your hooks when it reaches your jar, one jar after another, so if your code there uses another mod's classes, load after that mod (loadModAfter). Zabric's own classes are always there on a launch that runs entrypoints.
- Java mods and mod folders (package com.pzlauncher.zabric.mods): call from your main entrypoint or later, on any thread; the calls throw when Zabric did not run at game start or its entrypoints stopped.
- JavaMods: loaded() lists every jar ZombieBuddy loaded in this game session (mod id, path, SHA-256, and LoadPhase PRELOAD at game start, STARTUP in the first mod list, LATER in every later mod list: joining or leaving a server, and the main menu's mod reloads); lastPass() the jars of the latest mod list; servingJar(package) the loaded jar the game runs that package's classes from. A jar stays loaded until the game exits. inFolder(folder of mod folders, mod folder -&gt; the game's version folder name) reads the mods in it whose jar ZombieBuddy loads on a client, by ZombieBuddy's rules (folder, id, name, jar, package, and whether it runs at game start).
- LaunchOverride: request(Workshop item id -&gt; absolute path of a folder of mod folders) makes the next launch of the same side (client or dedicated server) use that folder in place of the item's mods folder, in every mod list of that launch, Lua and Java alike. The next game start reads and deletes the request; an invalid one is discarded whole, with an error in console.txt, which also names each item it uses. Items that hold ZombieBuddy, Zabric or ZabricKotlin are refused. pending() is what the next launch reads, current() what this launch uses.
- WidenRoots (on the main thread): add(folder of mod folders) makes Zabric read the widening lists of the mods in it from the next game start on, while the folder exists; scanned(folder) tells whether this launch read them. A LaunchOverride's folders are read without it.
- Relaunch (package com.pzlauncher.zabric.relaunch, same calling rules, but on the main thread): restart(argument indices to leave out) quits the game and starts it again with the same program, command line, working folder and environment, minus those arguments, through a small helper process; it throws and leaves the game running when that cannot be set up. unavailable() is null when a restart is possible, otherwise the reason (Windows clients only). arguments() is this launch's argument list. When the game cannot start again after it quit, the player gets a message box, Zabric/relaunch.log in the game's cache folder, and a notice on the next main menu.
- Hooks, setup: compileOnly "com.pzlauncher:zabric:&lt;version&gt;" and annotationProcessor "com.pzlauncher:zabric-processor:&lt;same version&gt;" (Maven Central), plus the game jar and ZombieBuddy.jar from your install (compileOnly). Processor options: zabric.modId (your mod id) and zabric.javaPkgName (the generated glue goes there), plus zabric.glueClass when one mod is built from several compilations. The processor checks each hook at compile time and writes the loader glue into your jar.
- Hooks, API (package com.pzlauncher.zabric.hook; Mixin and MixinExtras names): @Hooks(Target.class) marks a final class of static handlers (targets = "a.b.C" for classes you cannot name; in Kotlin a top-level object). @Inject(method = "name", at = @At("HEAD" or "RETURN")) runs a handler there, with a CallbackInfo; cancellable lets it skip the target at HEAD or set the return value. @ModifyReturnValue returns a new return value. @ModifyVariable(at = @At("HEAD"), argsOnly = true) returns a new argument. @Share("key") LocalRef passes a value between the handlers of one call. Zabric only: @Self is the target's this; @At("FINALLY") runs after the target returns, throws or was cancelled (@Thrown Throwable), to undo what HEAD changed; always = true runs a handler while its gate is inactive too. Overloads need "name(descriptor)". Anything else (other @At values, @Redirect, ...) is a compile error.
- Hooks, gates: a hook class without a gate uses your mod's default gate: the first exception from a handler, or a hook ZombieBuddy did not weave, stops all your mod's hooks for the session, logged as "[Zabric] &lt;mod id&gt;: hooks stopped ...". For a smaller scope, name a gate in @Hooks(gate = ...): a HookGate with a public static final INSTANCE, or a Kotlin object. Its active() is checked on every call; its failed() gets what handlers throw and hooks that were not woven, for a preloaded mod also before the game's log is up. A thrown exception never reaches the hooked method, which goes on as without the handler. Zabric checks the targets of default-gate hooks itself; a gate of your own calls ZabricHooks.gateProblem(gate) before it turns active, no earlier than your main entrypoint (it loads the targets).
- Hooks, timing and order: hooks run while your mod is in the mod list, from the first mod list Zabric processes (when main entrypoints run). They add no restart of their own. A mod kept running at game start has them on after its preLaunch entrypoint, whatever the list, then follows the list (from the first list on its first launch, or in a class ZombieBuddy loaded unwoven). "Zabric-Hooks: launch" in its manifest keeps them on for lists that lack it too, e.g. a server's: for client-side UI only, as they also act on servers and saves without your mod. Without a preLaunch entrypoint, or with another value, it fails like an empty entrypoint class. Across mods, the load order decides which hook wraps which; there is no priority. Within your mod, hook classes run by name and their handlers in declaration order.
- Hooks from game start: as Zabric cannot load game classes or log yet, it checks default-gate targets from class files: methods as each class loads (a mismatch stops your hooks before its code runs), classes at the first mod list, when it logs what it held. ZombieBuddy, though, loads the glue's signature types when it preloads your jar (each target's argument and return types, arrays excepted, and the target class with @Self): to leave game classes to the game, hook methods whose signatures name only JDK types, without @Self.
- Loader progress: LoaderProgress.listen(modId, listener), where modId is the mod whose jar holds the listener's class (else listen throws), hears each Java mod jar ZombieBuddy loads for a mod list (index, total, mod id; before and after) on the game thread while your hooks are on; register at preLaunch for the first list. If it throws, or Zabric cannot follow ZombieBuddy, your hooks stop.
- Hand-written ZombieBuddy @Patch classes: the processor rejects them. @UnsafeLoaderPatch on the class lets it compile, with a warning. Not recommended: such a patch has no Zabric gate, error catching or target check, and Zabric takes no responsibility when it breaks, e.g. when Zabric moves to another loader.
